# Архитектура

Certificate Viewer — статическое browser-only приложение на Next.js. `output: "export"` создаёт каталог `out/`; серверная часть во время работы отсутствует.

## Архитектурные принципы

- пользовательские сертификаты не покидают вкладку браузера;
- парсер не зависит от React и может быть перенесён в Web Worker без изменения UI-контракта;
- формат входного файла определяется по содержимому, а не только по расширению;
- результат парсинга нормализуется в собственную доменную модель;
- UI не делает вывод «сертификат доверенный», если проверена только структура;
- новые сетевые функции должны быть отдельным явно включаемым режимом.

## Поток данных

1. Пользователь выбирает файл через dropzone или `Ctrl+O` / `Cmd+O`.
2. `parseCertificateFile` проверяет общий размер и определяет PEM или DER по содержимому.
3. PEM bundle делится на блоки с лимитом 100 сертификатов; каждый декодированный сертификат ограничен 2 МБ.
4. Base64 PEM проверяется до ASN.1-разбора.
5. ASN1.js декодирует DER, PKI.js строит модель X.509.
6. Данные нормализуются в `ParsedCertificate`.
7. Web Crypto рассчитывает SHA-256 и SHA-1 fingerprints.
8. React отображает данные как текст и позволяет локально скачать JSON или PEM.

Файл существует только в памяти вкладки. Приложение не использует API routes, `fetch`, аналитику, телеметрию, cookies или браузерное хранилище для сертификатов.

## Границы модулей

- `src/app` — композиция страницы, metadata и глобальные стили;
- `src/components/layout` — общий каркас приложения;
- `src/features/certificate-viewer/components` — dropzone, workspace и отображение сертификата;
- `src/features/certificate-viewer/lib` — определение формата, ASN.1/X.509-парсинг, OID и форматирование;
- `src/features/certificate-viewer/types` — доменная модель результата;
- `src/lib` — небольшие общие утилиты.

## Модель доверия

Текущая версия выполняет структурный разбор, но не подтверждает доверие.

Нужно различать четыре независимых результата:

1. структура ASN.1/X.509 распознана;
2. сертификат находится внутри периода действия;
3. криптографическая подпись подтверждена загруженным issuer;
4. цепочка заканчивается доверенным корнем и не отозвана.

В версии 0.2.0 реализованы первые два пункта. Проверка подписи и загруженной цепочки запланирована на 0.3.0. Системное доверие и отзыв не входят в текущую browser-only модель.

## Производительность и защита

Текущие ограничения:

- 10 МБ на входной файл;
- 2 МБ на отдельный сертификат;
- 100 сертификатов на PEM bundle.

Парсинг пока выполняется в UI-потоке. Следующий уровень защиты от CPU/память DoS — Web Worker, тайм-аут и отмена обработки.

## Доставка

- `ci.yml` проверяет типы, lint и production build;
- `security.yml` запускает production audit, CodeQL и Dependency Review;
- `deploy-pages.yml` собирает приложение с repository-aware `basePath` и публикует `out/` через GitHub Pages;
- Dependabot предлагает только minor/patch-обновления;
- основные Actions обновлены до `checkout@v7`, `setup-node@v7`, `upload-pages-artifact@v5`, `deploy-pages@v5` и `codeql-action@v4`.

## Временный технический долг сборки

Текущий `package-lock.json` содержит URL внутреннего npm mirror среды первоначальной сборки. GitHub Actions не может получить эти пакеты, поэтому workflow временно удаляют lock-файл и устанавливают зависимости из `registry.npmjs.org`.

Правильное окончательное решение:

1. регенерировать lock-файл через публичный registry;
2. проверить отсутствие внутренних URL;
3. закоммитить новый lock-файл;
4. вернуть `npm ci` и cache во все workflow.

До выполнения этих шагов сборка работает, но не является полностью воспроизводимой по lock-файлу.
